## Context

当前 FastAPI 应用已经提供问答、搜索、来源、实体、关系和状态接口，`web/index.html` 仅把问答能力做成单页原型。M7 正在 ECS 上持续采集，资料数量和状态会不断变化；M8 后续还会把线上读取从 SQLite 切换到 RDS。因此 UI 不能假设语料已经完整，也不能直接依赖数据库实现细节。

## Goals / Non-Goals

**Goals:**

- 在现有技术栈内交付一个可立即使用的私有只读界面。
- 让用户能够问答、筛选搜索、展开来源详情并查看当前覆盖状态。
- 固定浏览器依赖的 JSON 契约，使新增资料和未来读取适配器切换对 UI 透明。
- 对加载中、空结果、证据不足和服务错误提供明确反馈。

**Non-Goals:**

- 本变更不完成 PostgreSQL/RDS 读取适配器。
- 不增加登录、公网发布、管理写操作或大模型生成。
- 不承诺在 M7 采集结束前达到最终召回率或完整分类覆盖。

## Decisions

### 保持无构建的单页应用

继续使用一个静态 HTML/CSS/JavaScript 页面，通过页面内导航切换问答、搜索和资料概览。这样不引入 Node 构建链或新运行依赖，适合当前单用户私有产品，并能随 FastAPI 一起部署。备选的 React/Vue 工程会带来此阶段不必要的构建与部署复杂度。

### 新增稳定的浏览元数据接口

新增只读 `GET /api/catalog`，返回解析完成资料的类型、版本、上下文及状态计数。UI 不直接解释内部表，也不通过管理同步接口获取筛选项。现有 `/api/search` 和 `/api/sources/{id}` 继续作为结果与详情契约。

### 使用 URL hash 表示页面状态

`#ask`、`#search`、`#coverage` 和 `#source/{id}` 让页面可前进、后退并可复制来源详情位置，同时不要求服务端增加 SPA fallback。搜索参数保存在表单和当前 URL 查询片段中，刷新后仍可恢复。

### 把资料完整度与答案可信度分开

覆盖页展示已发现、已抓取、已解析和跳过数量，并明确“仍在采集”不等同于服务异常。问答仍沿用现有证据状态与逐主张引用，不用资料总量替代答案支持检查。

### 为未来版本更新保留增量边界

UI 只查询最新 API 状态。版本更新时由采集端重新发现目录、对详情内容做哈希比对、仅解析和入库新增或变更项，再增量更新索引；UI 无需重新构建。删除内容先标记失效，避免无审计的物理删除。

## Risks / Trade-offs

- [单文件前端随功能增加会变大] → 保持本阶段组件和状态管理简单；达到多人协作或复杂审核需求时再拆分构建工程。
- [当前 SQLite 与未来 RDS 查询能力不同] → 测试 HTTP 响应契约，不让页面依赖 SQL 或 SQLite 特有字段。
- [采集中计数可能快速变化] → 每次进入覆盖页重新请求，并显示这是即时快照。
- [来源标题或版本缺失] → UI 使用可理解的兜底标签，原始官方链接仍保留。

## Migration Plan

1. 先发布新增只读接口与兼容测试；现有客户端不受影响。
2. 发布新的静态页面；失败时可只回滚 `web/index.html`。
3. ECS 私有访问验证搜索、详情和状态；不启动或停止任何采集服务。
4. 后续 RDS 读取层实现相同接口契约，再切换部署配置。

## Open Questions

- 登录方式、域名和 HTTPS 在准备公网或多人访问前决定。
- 版本筛选在资料版本字段覆盖率提高后，是否改为语义化范围选择。
