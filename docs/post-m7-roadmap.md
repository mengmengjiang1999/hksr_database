# M7 之后的阶段路线图

> 状态：初步规划。各阶段以验收条件为准，不预先承诺日期。

## 目标

M7 完成后，项目将拥有一条在 ECS 上运行的米游社官方内容采集链路，原始响应保存在私有 OSS，合格内容增量进入 RDS。后续工作的重点应从“把数据搬上云”逐步转向“让云端数据真正服务问答、扩大官方资料覆盖、验证质量，再决定是否开放使用”。

```text
M7 米游社采集入库
  → M8 云端主数据与检索
  → M9 其他官方来源扩充
  → M10 全量质量评测
  → M11 云端产品完善
  → M12 受控开放与长期运维
```

开发、测试、真实采集和部署原则上都在 ECS 上进行；本地只用于必要的代码编辑与查看，不设置强制的主机限制。

## M8：RDS 成为应用主数据源

目标：让 ECS 上的 API、检索和问答直接使用 RDS 中的正式数据，不再依赖随项目同步的 SQLite 作为线上读取库。SQLite 只保留为采集暂存和可重建缓存。

主要工作：

- 将来源、文本片段、实体、关系和证据查询切换到 PostgreSQL；
- 在 RDS 中建立全文、实体和必要的向量检索索引；
- 保持稳定证据 ID、引用展开、拒答和关系审计行为不变；
- 完成 ECS 上的回归测试、性能抽样和新旧查询结果对照；
- 明确数据迁移、索引重建和应用发布的标准命令。

完成标准：ECS 应用只依赖 RDS 即可完成现有搜索和问答；相同测试集的引用与结论没有无解释退化。

## M9：扩充其他官方资料

目标：在米游社文章之外，逐类补齐角色 Wiki、主线任务、阅读物以及能获得官方文本的视频资料。

主要工作：

- 每类来源先做小批量试采，再逐步扩大；
- 沿用 M7 的断点续传、限速、OSS 原始层、分类和批次审计；
- 优先采集文本稳定、剧情价值高的角色、任务和阅读物；
- 没有官方字幕的视频继续只保存元数据，不生成字幕充当证据；
- 为版本、时间线、语言和资料类型补充统一标签。

完成标准：预定官方来源清单均达到可解释的“已完成、已排除或待人工审核”状态，所有入库片段都能追溯到官方原始资料。

## M10：全量检索与问答质量评测

目标：验证样本阶段表现良好的检索和问答逻辑，在扩充后的真实语料上仍然可靠。

主要工作：

- 建立覆盖角色、事件、时间线、关系、版本冲突和无答案问题的人工测试集；
- 重新评测全文、实体和向量混合检索；
- 统计 Top 5 证据召回率、引用覆盖率、拒答准确率和错误类型；
- 优先修复数据缺失、切分错误、实体歧义和版本混用，再调整排序参数；
- 对高风险回答做人工抽查并形成固定回归集。

完成标准：核心测试集 Top 5 证据召回率达到 85% 至 90%，事实性主张均有有效引用，无答案问题能够稳定拒答，主要失败类型已有清晰记录。

## M11：云端产品完善

目标：把当前原型整理成便于持续使用和维护的私有云端产品。

主要工作：

- 完善问答、搜索、来源详情、实体关系和人工审核界面；
- 增加运行状态、采集批次、失败任务和待审核内容的管理页面；
- 为应用配置身份验证、HTTPS、日志轮转、健康检查和最小权限；
- 建立可重复的 ECS 测试与部署流程，减少手工步骤；
- 根据真实使用数据记录 ECS、RDS 和 OSS 成本。

完成标准：授权用户可以稳定使用云端界面，维护者能够查看数据状态、处理审核项并完成可重复部署。

## M12：受控开放与长期运维

目标：在数据质量和私有运行稳定后，再决定是否扩大访问范围以及是否启用长期自动同步。

主要工作：

- 先进行少量受邀用户测试，收集真实问题和失败案例；
- 评估官方内容展示、缓存和再分发边界；
- 经明确批准后启用定时增量采集，并持续观察限流与失败情况；
- 建立基础告警、容量趋势和月度成本记录；
- 根据实际连续用量，再决定 ECS/RDS 是否从按量付费转为包年包月或其他节省计划。

完成标准：访问范围、内容边界、更新频率、费用方案和日常维护责任均有明确决定。

## 推荐优先级

M7 结束后应立即启动 M8。M9 可以在 M8 的数据库读取层稳定后分来源推进；M10 必须基于扩充后的真实数据进行；M11 和 M12 不应早于质量评测。备份恢复演练暂不列入这些阶段，除非以后出现正式上线、多人使用或更高数据安全要求。
