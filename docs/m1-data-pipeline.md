## 1. 阶段结论

M1 已完成从来源发现到本地全文检索的最小闭环：

```text
来源发现
  ↓
SQLite 登记与去重
  ↓
官方 JSON 抓取和本地原始响应保存
  ↓
稳定内容哈希判断是否需要重新解析
  ↓
Wiki RPG / Wiki 页签 / 米游社文章解析
  ↓
Source / Document / Chunk 入库
  ↓
SQLite FTS5 中文全文索引
  ↓
返回带页面、来源类型和栏目路径的检索结果
```

五个 M0 样本已全部完成真实数据导入和检索，未出现抓取或解析失败。

## 2. 已实现能力

### 2.1 来源发现

支持三种发现入口：

- M0 样本清单；
- Wiki 关键词搜索；
- 米游社官方账号文章列表及游标分页。

Wiki 搜索只登记 `/wiki/content/{id}/detail` 词条。搜索中混入的米游社文章不会直接登记，因为其中可能包含玩家内容。官方文章统一从已认证官方账号列表发现，并逐条检查：

- `post_status.is_official`；
- 用户认证标签包含“官方账号”；
- 文章 ID、标题和发布账号可用。

### 2.2 幂等登记

来源使用 `(provider, external_id)` 唯一约束。同一清单、搜索结果或官方账号页面重复执行不会创建重复来源。

### 2.3 原始响应与增量更新

原始 JSON 保存到：

```text
data/raw/{provider}/{external_id}.json
```

该目录不提交版本库。写入时先生成临时文件，再进行原子替换，避免中断后留下半份响应。

系统分别记录：

- 原始响应 SHA-256；
- 可检索内容 SHA-256；
- 响应字节数；
- 抓取时间；
- 原始文件路径。

米游社视频响应中的浏览统计、回复数量和临时签名播放地址会变化，但不代表官方内容发生变化。内容指纹只纳入标题、正文、官方身份、发布时间和稳定视频 ID 等字段，从而避免无意义的重复解析。

### 2.4 三类解析器

#### Wiki RPG 模板

处理角色等 `rpg_new_tmp_content` 页面：

- 按模块生成文档；
- 二次解码组件中的 JSON 字符串；
- 过滤模板内部 ID、URL、图片、音频和文本映射元数据；
- 跳过隐藏模块；
- 将攻略、推荐、画廊、考据等模块标记为不可进入证据索引。

#### Wiki 普通页签

处理阅读物、任务等 `contents[].text` 页面：

- 按页签生成文档；
- 从 HTML 提取可检索文本；
- 保留页面标题、页签和顺序；
- 按长度生成文本片段。

#### 米游社官方文章

- 强制验证官方文章状态和账号认证；
- 提取标题、正文、发布时间和更新时间；
- 保存发布者、认证标签和视频 ID；
- 不保存临时签名视频地址；
- 将没有机器可读字幕的状态写入文档元数据。

## 3. SQLite 数据模型

### Source

保存来源身份和同步状态：

- provider 与 external_id；
- 来源类型和解析器；
- 页面 URL 和接口 URL；
- 标题、版本、远端时间；
- 官方身份状态；
- 原始响应及内容哈希；
- discovered、fetched、parsed、error 状态；
- 最近错误信息。

### Document

保存来源内部的栏目或页签：

- source_id；
- document_key；
- 标题和 section_path；
- 内容类型和位置；
- evidence_eligible；
- 结构化元数据。

### Chunk

保存可检索证据片段：

- document_id；
- chunk_key；
- section_path；
- speaker；
- 文本和位置；
- 内容哈希和元数据。

## 4. 全文索引

第一版使用 SQLite FTS5。运行环境支持 `trigram` tokenizer，适合中文子串检索；代码在不支持 trigram 时回退到 `unicode61`。

索引首次建立后通过 SQLite 触发器跟随 Chunk 的插入、修改和删除自动更新，避免重新解析来源后继续返回旧证据。`index` 命令用于首次建立和完整重建。

检索结果包含：

- chunk_id 和 source_id；
- 来源标题与类型；
- 页面 URL；
- section_path；
- 文本和 BM25 分数。

## 5. CLI

### 样本清单发现

```bash
python3 -m app.cli discover
```

或指定清单：

```bash
python3 -m app.cli discover --manifest data/m0/sample-manifest.json
```

### Wiki 和官方账号发现

```bash
python3 -m app.cli discover \
  --wiki-query 阿格莱雅 \
  --official-account-uid 288909600 \
  --pages 1
```

### 抓取、解析和索引

```bash
python3 -m app.cli fetch
python3 -m app.cli parse
python3 -m app.cli index
```

### 状态和搜索

```bash
python3 -m app.cli status
python3 -m app.cli search 孤独逐火 --limit 5
```

可以通过全局 `--database` 参数使用独立数据库：

```bash
python3 -m app.cli --database /tmp/test.sqlite3 status
```

## 8. 当前限制

- Wiki 搜索适合按关键词发现，后续仍需实现按频道的全量分页同步；
- 普通页签 HTML 会包含“折叠/展开”等少量界面词，需要进一步清洗；
- 当前切分以栏目和字符长度为主，尚未针对对话轮次、说话人和剧情场景优化；
- speaker 字段已预留，但当前通用解析器尚未可靠填充；
- 全文检索只有 BM25，尚未加入向量检索、别名和重排；
- 视频完整字幕与时间戳证据仍未解决；
- 接口未观察到对第三方的稳定性承诺，需要保留失败重试、限速和结构监控。

## 9. M2 建议

M2 应以“检索正确证据”为唯一核心目标：

1. 建立 30 至 50 个初始问题与证据标注；
2. 优化任务对话、角色故事和阅读物的分段；
3. 提取说话人、任务场景和角色故事编号；
4. 建立实体和别名表；
5. 增加向量索引和混合排序；
6. 统计 Top 1 与 Top 5 召回率；
7. 召回率稳定后再进入答案生成。
