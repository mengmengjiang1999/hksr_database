# 游戏版本更新后的增量资料刷新

## 结论

正常版本更新不需要清空数据库、重新采集全部历史资料或重做用户界面。目标流程是重新读取官方目录，识别新增、变更和下线页面，只处理发生变化的内容，然后增量更新数据库和检索索引。

## 每次版本更新需要执行的工作

1. 重新运行 Wiki 目录发现，登记新的 `content_id` 和分类。
2. 对目录中的既有页面安排低频详情复查。Wiki 目录目前不能稳定提供可依赖的内容版本号或更新时间，因此不能只看目录判断正文是否变化。
3. 抓取详情后计算原始响应和规范化正文哈希：
   - 新 ID：保存 OSS 原始响应、解析并新增到正式库；
   - 已有 ID 且哈希变化：保留新的 OSS 版本，重新解析并更新正式库；
   - 已有 ID 且哈希不变：记录检查时间，不重复解析和入库。
4. 对目录中消失或接口已不可用的页面先标记为失效/下线，保留历史证据和审计记录，不立即物理删除。
5. 只重建受影响文本的全文、实体和后续向量索引，并运行固定的检索回归样例。
6. 核对新增分类、页面模板和字段。如果官方改变接口结构或出现新模板，再更新采集器、解析器和相应测试。

米游社官方账号补充内容使用相同原则：从最新文章开始发现，历史文章保留原检查点；新增或正文哈希变化的文章才进入后续处理。

## 不需要重复做的工作

- 不需要重新创建 OSS Bucket、RAM 策略、ECS RAM 角色或 RDS 实例。
- 不需要重新抓取和解析所有哈希未变化的历史页面。
- 不需要重新搭建前端。界面通过稳定 API 读取当前数据，新增资料入库后会自动进入搜索和覆盖统计。
- 不需要为了更新资料重新发布 UI；只有 API 契约、页面字段或产品功能发生变化时才需要发版。

## 当前实现状态

M7 的目录发现已经是幂等的：重复执行会保留已抓取/已解析状态，并把新 ID 加入队列。尚待完成的是对“已有 ID 的正文变化”进行受控复查、哈希比较和 RDS 增量同步；这属于 M7 任务 7.5。在它完成前，新 ID 可以自动加入，但已有页面被官方改写时仍需要一次显式刷新流程。

## 推荐发布门槛

每次版本更新至少确认：目录发现成功、详情接口错误率无异常、新增/变更数量可解释、解析失败为零或已列入人工处理、检索回归没有无解释退化。界面部署与资料刷新解耦，采集失败不会自动覆盖一个仍可使用的前端版本。
